# تقرير تدقيق الأمان والتحصين — المرحلة 11

آخر مراجعة للمصدر: 2026-10-03. هذا التقرير يصف ما أمكن إثباته من ملفات المشروع وترحيلاته؛ لم يتصل التدقيق بقاعدة Supabase المستضافة أو إعدادات لوحة التحكم.

## النتيجة المختصرة

- لم يظهر في فحص الترحيلات أي جدول عام أُنشئ في المشروع من دون عبارة تمكين RLS: 19 جدولًا عامًا مكتشفًا، وكلها لها `ENABLE ROW LEVEL SECURITY` في الترحيلات. جدول محاولات الحضور الجديد في مخطط `private` لا يمنح صلاحيات مباشرة لأدوار المتصفح.
- لم يظهر استخدام حرفي لـ `USING (true)` أو `WITH CHECK (true)` في ترحيلات التطبيق.
- أدوار التطبيق هي `STUDENT` و`TEACHER` و`ADMIN`. إنشاء الملف يتم عبر Auth trigger، وإسناد الدور العام يقبل الطالب أو المدرس فقط. حماية قاعدة البيانات تمنع المستخدم من تغيير دوره أو حالة المدرس مباشرة.
- مسارات القراءة والكتابة الحساسة تعتمد على RPC تتحقق من `auth.uid()` والدور أو الملكية. عمليات إدارة Classy الإدارية تتطلب فحص ADMIN داخل قاعدة البيانات؛ حماية المسار في React طبقة إضافية فقط.
- لم يُعثر على اعتماد للواجهة الأمامية على مفتاح service-role. ملف `.env` المحلي يحتوي أسماء إعدادات Supabase العامة للمتصفح فقط؛ لم تُطبع قيمه في هذا التقرير.
- فحص `npm audit` اكتمل بلا ثغرات معلنة في الاعتماديات وقت الفحص.
- `npm run lint` نجح، و`npm run build` نجح. ظهر تحذير Vite المعتاد بأن حزمة JavaScript الرئيسية تقارب 919 kB بعد التصغير؛ لا يؤثر على نجاح البناء.

## نموذج المصادقة والصلاحيات

- Supabase Auth هو مصدر هوية المستخدم. العميل يستخدم `getSession()` لاستعادة واجهة الجلسة، ويستخدم `getUser()` عند العمليات الحساسة في Auth وEdge Functions. لا تحفظ كلمات المرور في جداول التطبيق.
- `ProtectedRoute` و`RoleRoute` يمنعان عرض الصفحات أثناء التحميل ويتحققان من الملف والدور لتوجيه الواجهة. التفويض الفعلي موجود أيضًا في سياسات RLS وداخل RPC الحساسة.
- إنشاء المستخدم يمر عبر `auth.users` trigger. metadata لا تمنح ADMIN. استكمال إعداد Google يسمح بـ STUDENT أو TEACHER، ويظل ADMIN للتجهيز الإداري الموثوق.
- وظائف `SECURITY DEFINER` التي تتعامل مع البيانات الحساسة تستخدم `search_path = ''` وتُقيّد صلاحية EXECUTE حسب المستدعي؛ يلزم مراجعة صلاحيات قاعدة الإنتاج مباشرةً لأن الأذونات الفعلية غير قابلة للقراءة هنا.

## مصفوفة RLS المستنتجة من الترحيلات

هذه المصفوفة تصف مسارات قاعدة البيانات المعرفة في ملفات الترحيل، لا نتيجة استعلام حي. «RPC» تعني أن الكتابة/القراءة تمر عبر دالة تفحص الهوية والملكية، و«لا وصول مباشر» تعني أن سياسة أو منحة المتصفح المباشرة غير موجودة بحسب الملفات.

## الملفات والإيصالات

- `teacher-payment-receipts` و`student-payment-receipts` خاصان، حدّهما 5 MiB، وMIME المسموح به JPEG/PNG/WebP بحسب الترحيلات.
- `teacher-avatars` خاص وحدّه 2 MiB وMIME الصور نفسها.
- سياسات `storage.objects` تربط مسارات الإيصالات بصاحب الحساب والاشتراك والدفعة، وتسمح للأدمن بمراجعة الإيصال. قراءة الصورة تتم عبر signed URL قصيرة العمر. الصور لا تستخدم روابط عامة دائمة.
- قيود bucket تتحقق من الحجم ونوع MIME المسجل في Storage؛ فحص بايتات الملف الفعلية/إعادة ترميز الصور لم أجد له خدمة خادمية في المشروع. تظل هذه نقطة تحسين منخفضة إلى أن يظهر احتياج عملي أو معالجة صور على الخادم.

## Edge Functions والحضور وحذف الحساب

- `check-attendance` يعطل تحقق Gateway القديم في `config.toml` لكنه يتحقق من Bearer token بنفسه باستخدام Supabase Auth، ويأخذ هوية الطالب من المستخدم المتحقق منه، ثم يستدعي recorder ممنوحًا لـ service-role فقط.
- ترحيل `20261017000000_phase11_attendance_attempt_limit.sql` يضيف تقييد المحاولات. يجب تطبيقه بعد نجاح ترحيل Phase 10، ثم نشر `check-attendance`؛ دون الاثنين لن يعمل حد المحاولات في المشروع الحي.
- `delete-account` يتحقق من الجلسة عبر Auth، ويقبل STUDENT/TEACHER فقط، ثم يحذف ملفات المستخدم ويطلب حذف بياناته المرتبطة ويزيل Auth account. service-role مستخدم في Edge Function فقط، وليس في الواجهة. حذف الملفات والبيانات وAuth ليس معاملة واحدة؛ فشل حذف Auth بعد حذف البيانات يُسجل ويعيد رسالة دعم.
- أزيل استيراد CORS العام من الوظيفتين. أضف في Supabase Dashboard ضمن Edge Function Secrets متغير `APP_ALLOWED_ORIGINS` بقيم Origins الفعلية مفصولة بفواصل، مثال: `https://classy.example.com,https://www.classy.example.com`. أثناء التطوير فقط، إذا لم يُضبط المتغير، يُسمح بـ `http://localhost:5173` و`http://127.0.0.1:5173`.

## الإعدادات والاعتماديات وبيئة الإنتاج

- `.env` مستثنى من Git، و`.env.example` أصبح مستثنى من قاعدة `.env.*` حتى يمكن حفظ قالب بلا قيم سرية.
- لم يظهر في إعدادات Vite إلا `VITE_SUPABASE_URL` ومفتاح Supabase العام؛ لا يجوز وضع service-role أو كلمة مرور قاعدة البيانات تحت `VITE_*`.
- لا يتضمن المستودع إعداد استضافة إنتاجية معروفًا مثل Netlify/Vercel/Cloudflare headers. أضف عند تحديد المضيف: CSP متوافقة بعد اختبار Google OAuth وSupabase، `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy`, وHSTS على HTTPS.
- إعدادات Supabase Auth الحية (Site URL، Redirect URLs، تأكيد البريد، سياسات كلمة المرور، Origins) غير متاحة للفحص من ملفات Vite؛ تحقق منها يدويًا ولا تسمح بنطاقات wildcard غير لازمة.
- لم يوجد مجلد `.git`، لذا لم يُفحص التاريخ أو إعداد الريموت. لا يمكن الجزم أن ملفًا سريًا لم يُرفع سابقًا.
- لا توجد خطة نسخ احتياطي أو إعداد استضافة موثق في المستودع. فعّل نسخًا احتياطية ملائمة للخطة قبل الإطلاق، واختبر الاستعادة، واحتفظ بترحيلات قاعدة البيانات في المصدر.

| طالب يعدل `teacher_id`, `group_id`, price أو status في اشتراكه | عمليات الكتابة عبر RPC راجعها التدقيق | لم تُنفذ على أدوار حقيقية |
| مدرس يدير مجموعة/جلسة مدرس آخر | دوال الملكية وسياسات القراءة راجعها التدقيق | لم تُنفذ على أدوار حقيقية |
| مستخدم يستدعي RPC إدارية مباشرة | حواجز ADMIN ومنح EXECUTE راجعها التدقيق نصيًا | لم تُنفذ على قاعدة حية |
| قراءة/كتابة إشعار مستخدم آخر | RLS والحقول الممنوحة راجعها التدقيق | لم تُنفذ على Realtime حي |
| تخمين كود الحضور المتكرر | أضيف اختبار بنيوي للحد؛ يلزم تطبيق DB ونشر Edge Function | غير قابل للتحقق حتى النشر |
| CORS من origin غير مسموح | المنطق يرفضه في المصدر | يحتاج نشر الوظيفتين وتجربة preflight |
| حذف الحساب | تحقق الهوية والدور ومسار حذف الملفات والبيانات راجعها التدقيق | لم تُنفذ؛ تتطلب حسابات اختبار وبيئة آمنة |

اجتاز ESLint وفحص البناء. مررت ملفات Edge Functions على محلل TypeScript للتحقق من سلامة الصياغة، لكن Deno/Supabase CLI غير متاحين هنا لإجراء type-check خاص ببيئة Edge أو تشغيل اختبار تكاملي. فشل أول تشغيل للبناء بسبب قيد `spawn` في sandbox ثم نجح عند إعادة التشغيل المصرح به؛ لا يوجد فشل بناء متبقٍ.

## ما يلزم قبل اعتبار المرحلة مكتملة على الإنتاج

1. تطبيق ترحيل Phase 10 المصحح ثم ترحيل Phase 11 بالترتيب، والتأكد من نجاحهما دون أخطاء.
2. نشر `check-attendance` و`delete-account` من المصدر المحدّث، وضبط `APP_ALLOWED_ORIGINS` إلى نطاقات الموقع الفعلية.
3. في Supabase SQL Editor، تحقق من حالة RLS والسياسات والمنح والدوال على المشروع الفعلي، لأن ملفات الترحيل لا تثبت أن كل ترحيل طُبق.
4. جرّب مصفوفة Anonymous/Student/Teacher/Admin بحسابات اختبار منفصلة، خصوصًا تحديث الدور، IDOR، الإيصالات، RPC الأدمن، الحضور المتكرر، حذف الحساب، وRealtime.
5. راجع Auth URLs/إعدادات البريد/كلمات المرور، Storage bucket limits، أسرار Edge Functions، ونسخ قاعدة البيانات من لوحة Supabase.
6. اضبط HTTPS وSecurity Headers في مضيف الإنتاج بعد معرفة اسم المضيف، واختبر CSP مع OAuth وSupabase.
7. افحص Git history والريموت في المستودع الأصلي، ودوّر أي secret حقيقي سبق إدخاله في commit.
